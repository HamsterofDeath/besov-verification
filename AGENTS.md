# Repository instructions

## Agent roles

The organizer (also called coordinator, orchestrator, or managing supervisor) is dispatch-only: route assignments, immediately refill eligible capacity on completion, blockage, failure or idle events, consume compact claim/ownership/allocation/status receipts returned by assigned agents only for routing, and report. The organizer does not execute census queries, allocation probes or audits itself. Dispatch every discovered task or blocker to a bounded owner; never take it over while waiting. Provisioning and recovery owners prepare or recycle exclusive worktrees and resources. Implementers perform feature work and implementation validation. Independent reviewers use a different checked identity to review the exact commit and record authenticated verdicts. A dedicated integrator performs integrated checks, captures and packages integration evidence, uploads it, lands through the guarded serialized repository path, and reads back Done with no remaining claim where a taskboard is used.

The organizer never implements, tests, audits, captures, packages or uploads evidence, prepares or recycles worktrees, repairs environments, acquires implementation/review/integration claims, or lands changes. Instructions below that call for those operations apply to the assigned execution owner. Every owner keeps its own checked identity and required claim, with an exclusive worktree and one feature branch. Preserve independent exact-commit review, all quality and security gates, guarded pushes, and serialized landing; never use pull requests, force pushes, shared credentials, or an unreviewed direct push to main/master.

## Local-only validation

- Never run CI in GitHub Actions or any other GitHub-hosted workflow for this project.
- Run all builds, tests, lint, coverage, release checks, and other validation locally.
- Do not add, enable, trigger, or rely on GitHub CI workflows or required GitHub status checks.
- When legacy push-triggered workflows still exist, include [skip ci] in every pushed commit message.
- Record the local validation commands and results in the relevant ticket or handoff.

## BLG common block

Every agent and every runner follows one lifecycle: the served BrainLiftGames workflow. Read it with
`taskboard instructions get --project KEY --role ROLE` (roles: organizer, implementer, reviewer, integrator, setup)
before your first claim, and again when a refusal names a rule you do not recognize. The AGENTS.md common block and
the MCP instructions are generated summaries of that workflow; the workflow wins when they differ.

### Roles

- **Organizer** (also orchestrator or coordinator): only dispatches bounded assignments, consumes compact receipts and
  immediately refills eligible capacity. It never implements, tests, reviews, packages evidence, claims, merges,
  lands, deploys, provisions or recovers.
- **Implementer**: owns one ticket from claim until Done, including FAIL returns. It keeps its worktree and harness
  session until Done (workflow section 6).
- **Independent reviewer**: its own reviewer credential and worktree; checks the exact producer commit against the
  ticket's Definition of Done and returns PASS or FAIL. It never repairs.
- **Dedicated integrator**: its own checked `supervisor` session; fetches the most recent main immediately before
  merging the unchanged reviewed producer, resolves conflicts in the merge commit preserving both sides' intent,
  runs integrated checks, lands through the serialized landing lock and reads back Done and a null claim.
- **Setup/recovery worker**: provisioning, checkouts, identities, audits, deployment and recovery under assigned
  authority.
- A deterministic runner performs the claim, keep, release, resume and park steps for its agents and follows the
  same rules.

### Owner rules

- **R1 A ticket is its own approval (2026-09-30).** Creating a ticket approves everything implied as necessary to
  finish it: screenshots, captures, renders, videos, image generation, device installs, dependencies, builds, tests
  and evidence uploads. Permission gates written into a ticket count as granted; do the step and note it in the
  handoff. Still binding: safety bans on destructive or risky commands, secrets, other agents' claims and branches,
  owner prohibitions quoted verbatim, and real outside consent (store publishing, spending money, contacting people).
- **R2 Role-specific model defaults (2026-10-02).** Supervisors dispatch development with their actual inherited
  model and never develop themselves. Independent review uses an available faster counterpart from the same family.
  An explicit user choice overrides both. Resolve model names from the live catalog; never guess or relabel a model.
  The reviewer is a different agent with its own credential; never substitute self-review. The implementer's cheap
  pre-review (workflow section 6) is part of implementation, not a review.
- **R3 Dispatch-only organizer.** Organizers, orchestrators and coordinators only dispatch, route compact results and
  refill eligible capacity. Implementers, independent reviewers, dedicated integrators and setup workers do all
  execution; the organizer never takes an execution or integration claim.
- **R4 No machine-local paths (2026-09-30).** Tickets, comments, evidence summaries and handoffs never contain drive
  letters, home or temp folders, network shares or WSL mounts. Upload the file as evidence or link a committed file
  by its full 40-character commit SHA.
- **R5 Cheap-label reservation (2026-10-05, amended 2026-10-09).** Tickets labelled `cheap` are reserved for
  cheap-class models (DeepSeek, GLM, flash, Haiku and Kimi 2.x class). Haiku means Claude Haiku 5.5 and later Haiku
  releases. An expensive model never claims one, in any phase, unless the owner says so. The server enforces this at
  claim admission in every phase with `cheap_label_reserved`, classifying a model by the live catalog's explicit
  `Cheap: yes` marker. A separate owner/admin identity may grant or revoke an audited per-ticket override through
  `PUT /model-routing/tickets/{ticketKey}/cheap-label-override`; it does not waive other admission gates.

### Branch workflow

- One ticket per branch. Work in an exclusive worktree on your own feature branch. Never push `main` or `master`;
  only the dedicated integrator lands, through the repository's serialized landing path.
- No pull requests, no force-push, no rebase or rewrite of a published producer. Preserve foreign work, branches,
  claims, sessions, worktrees and processes.
- Continue authorized work until it is complete. When a command fails and the safe correction is clear, fix it
  within scope and rerun the affected checks without asking again. A failed check blocks only the dependent action.
- Never bypass branch protection, claims, integration locks, independent review, security checks or release
  criteria. Stop and report a concrete blocker only when no safe authorized recovery remains; say what was tried and
  the exact input or authority needed.

### Local-only validation

- Run builds, tests, coverage and release checks locally. Never trigger or rely on GitHub-hosted CI.
- Every pushed commit message contains `[skip ci]`.
- Record the local validation commands and their results in the ticket handoff.
- Reuse a green run instead of rerunning it while the tested tree is unchanged: `taskboard evidence reuse` decides and
  records it, and only a run that passed on the exact producer SHA is reusable.
- Use only the HamsterofDeath account and its owner-qualified HTTPS Git repositories; keep the pre-push guard enabled.

### Integration conflict resolution

- **Most recent main:** fetch the most recent main immediately before each merge. Merge the unchanged reviewed
  producer with no rebase or rewrite; resolve conflicts in the merge commit, keeping the reviewed producer as a parent.
- **Generated files:** regenerate them with the repository's generator; never hand-merge generated output.
- **Hand-authored conflicts:** resolve them so that both sides' intent survives. A conflict alone is not a FAIL.
- **Integrated checks:** run the required checks on the resolved result. If main advances before landing, refresh
  and re-resolve against the new main, rerun affected checks and use the serialized landing lock; never force-push.
- **Recorded resolution:** record integration evidence under the live integration lease: the main SHA, producer SHA,
  conflicted paths, resolution diff relative to the automatic merge, and check results. Independent review of the
  unchanged producer remains required; integration evidence never replaces it.
- **When it still bounces:** only when resolution needs a product decision, or integrated checks still fail after a
  bounded attempt. FAIL evidence names the decision or the attempted resolution and which checks still fail.
- **Batch integration (TASKBOARD-636):** take members in priority order and merge them in sequence onto the most
  recent main, resolving as above. Bounce only the member that cannot be resolved; continue landing the rest.
